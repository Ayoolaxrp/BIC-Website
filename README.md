# Babcock Investors Club — Website (React)

Production-ready React site for the Babcock Investors Club (BIC) at Babcock University.
Vite + React 19 + React Router 7 + Framer Motion, with a Supabase backend (Postgres +
Auth + Row Level Security) and Paystack payments.

## Quick start (local dev)

```bash
cd bic-react
npm install
cp .env.example .env   # then fill in your keys (see below)
npm run dev            # http://localhost:5173
```

The site works **without any keys** — forms fall back to a local queue stored in the
browser. Add keys to unlock the full experience.

## What's inside

| Area | Details |
|---|---|
| Public pages | Home, About (23-exec team), Membership, Events, Blog, Sponsorship, Contact |
| Member portal | `/member` — sign up / sign in, profile (name, sector, phone, bio), membership status, RSVP history, member resources, community group links |
| Admin console | `/admin` — manage events, curated + club-written articles, resources, newsletter posts; view all submissions and a Members-by-Sector breakdown |
| Payments | Paystack Pop checkout (₦5,000 membership fee, event tickets) |
| Data layer | Supabase Postgres + RLS; anonymous inserts for forms; local-storage fallback offline |
| Downloads | Real club-produced PDFs/CSV in `public/resources/` (generated by `scripts/generate-resources.cjs`) |
| Blog | 11 curated, real articles (Nairametrics) with verified URLs; admins can add more |
| SEO | Meta/OG tags, `sitemap.xml`, `robots.txt`, route-level code splitting |

## 1. Set up Supabase (database + auth + admin user)

1. Create a free project at <https://supabase.com> → **New project** (name: `bic`, region:
   choose closest to Nigeria, e.g. `eu-central-1` or `eu-west-2`). Wait for provisioning.
2. Open **SQL Editor** → paste the entire contents of `supabase/schema.sql` → **Run**.
   This creates all tables, triggers, and row-level-security policies. Safe to re-run.
3. Enable email auth: **Authentication → Providers → Email** (enabled by default).
   For development you may disable "Confirm email" so you can sign in instantly;
   keep it ON for production.
4. Get your keys: **Project Settings → API** → copy the **Project URL** and the
   **anon public** key (NOT the service_role key — never expose that).
5. Create `.env` in `bic-react/`:

   ```env
   VITE_SUPABASE_URL=https://YOUR-PROJECT.supabase.co
   VITE_SUPABASE_ANON_KEY=eyJhbGciOi...
   VITE_PAYSTACK_PUBLIC_KEY=pk_live_xxxxxxxxxxxxxxxx
   ```

6. **Create your admin users** (do this after the site is deployed, or now):
   - Go to the site → `/member` → **Create an account** (use a real email + password).
   - Or create the user in **Authentication → Users → Add user**.
   - Then run **`supabase/promote-admins.sql`** in the SQL Editor — it promotes
     all 23 executives to admin in one shot. **Edit the placeholder emails first**
     to each exec's real registered email. It also assigns each sector chairperson
     their community (`sector` column), which drives sector-tagged resources.
   - Individual promotion if you prefer:
     `update public.profiles set role='admin' where email='you@example.com';`

   That's it — each promoted email can sign in at `/admin` and sees the same
   console (events, articles, resources, newsletter, submissions, member sectors).

> ⚠️ **Security note:** the `anon` key is safe to ship in the browser only because
> every table is locked down with RLS policies — the public can insert into form
> tables and read events/articles/resources, but only admins can read submissions
> or manage content. Never use the `service_role` key in the frontend.

### Google sign-in (optional)

1. **Supabase side:** **Authentication → Providers → Google** → toggle enabled,
   paste the Client ID + Secret (see Google Cloud steps below).
2. **Google Cloud Console** (<https://console.cloud.google.com>):
   - **APIs & Services → OAuth consent screen** — configure the app name + support email.
   - **Credentials → Create Credentials → OAuth client ID → Web application**.
   - **Authorized JavaScript origins**: `http://localhost:5173` (dev) and your
     production URL (e.g. `https://your-app.vercel.app`).
   - **Authorized redirect URIs**: paste the Supabase callback exactly as shown in
     the Supabase Google provider page (format `https://<project-ref>.supabase.co/auth/v1/callback`).
   - Copy the Client ID + Secret back into Supabase and save.
3. **Redirect URLs**: **Authentication → URL Configuration** → set **Site URL** to
   your production URL and add `https://your-app.vercel.app/**` (plus preview
   wildcards `https://*-your-team.vercel.app/**`) to **Redirect URLs**. Forgetting
   these is the #1 cause of OAuth "invalid redirect" errors.

### Linking accounts to student emails (important)

Membership is tied to a **Babcock student email** (`@babcock.edu.ng`):

1. **Client-side** (already done): the `/member` signup form only accepts
   `name.lastname@babcock.edu.ng`, and the Membership application requires the same.
2. **Server-side** (do this in Supabase for real enforcement):
   **Authentication → Providers → Email → Advanced settings** → set
   **"Allow signups from specific email domains"** to `babcock.edu.ng`.
   This stops anyone from registering with a non-Babcock email, even if they
   bypass the UI.
3. Optionally enable **"Confirm email"** — Supabase then emails a confirmation
   link, proving the applicant owns that inbox. For a university club this is the
   strongest practical verification without Babcock IT integration.

> True "is this student enrolled?" verification would require Babcock IT (an API
> or LDAP hook) — out of scope for a club site. Email-domain restriction +
> confirmation is the industry-standard approach for student orgs.

## 2. Paystack (membership fees + event tickets)

1. Sign up at <https://paystack.com> (Nigeria).
2. **Settings → API Keys & Webhooks** → copy your **Public key** (starts with `pk_live_`).
3. Put it in `.env` as `VITE_PAYSTACK_PUBLIC_KEY`.
4. For testing use a `pk_test_` key — you can test checkout with
   `test@example.com` and card `4084 0840 8408 4081` (test mode only).

Membership fee is `₦5,000` (constant `MEMBERSHIP_FEE` in `src/pages/Membership.jsx`).

## 3. Deploy to Vercel

1. Push the repo to GitHub, then on <https://vercel.com> → **Add New Project** →
   import the repo. Root directory: `bic-react`.
2. Add the three environment variables from above under **Settings → Environment Variables**.
3. Deploy. `vercel.json` in the repo already routes all paths to `index.html` (SPA).
   Netlify users: `netlify.toml` is included too.
4. Set a custom domain (e.g. `babcockinvestorsclub.org`) in Vercel → Domains.
5. After the first deploy, do step 1.6 (create the admin user) from a browser.

## Sectors, member profiles & community groups

- Members pick a **primary sector** when they apply (Crypto, Forex, Securities,
  Real Estate, or General) and can change it anytime from their `/member` profile.
  Profiles also store phone + bio, editable by the user.
- The Admin console **Overview** shows a **Members by Sector** breakdown (from
  `member_applications.sector`) so each executive can see how their community is
  growing, and every application lists its sector in the Submissions tab.
- The Member portal has a **Community Groups** panel with a group chat per sector.
  Links live in `src/lib/sectors.js` (`GROUP_LINKS`) — replace the `REPLACE_*`
  placeholders with the real WhatsApp/Telegram invite links before launch.

## Demo mode (no test accounts)

Until Supabase is configured, the site runs in **demo mode** with no stored
accounts — test credentials were removed before launch so nothing sensitive ships
in the client bundle. Once `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` are
set, real Supabase users take over automatically.

## Local queue & data migration

When the site runs without Supabase, every form submission is stored in the browser
under `bic_local_queue`. After connecting Supabase, submissions go straight to the
database — the local queue is kept for reference/export via the Admin console's
submissions tab once data exists.
